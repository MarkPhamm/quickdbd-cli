# `qdbd mcp`: let AI agents read your schema (qdbd 0.3.0, extension 0.5.0)

## Context

qdbd compiles schema files into diagrams for people. AI agents (Claude Code, Claude Desktop, Cursor, VS Code Copilot) can't use any of that today. They read raw `.txt`/`.dbml` files and guess at the joins.

`qdbd mcp` is an MCP server over stdio that hands agents the *compiled* schema: resolved tables, keys, relationships with cardinality, docs, tags, selectors, join paths with SQL, validation and git diffs.

**Your decisions:**
- **Jobs.** All four: explain the schema, write SQL with the right joins, edit schema files safely, review schema changes.
- **How it's built.** Built-in, with no new runtime dependencies.
- **Scope.** The core tools, plus a diagram-image tool, plus VS Code auto-setup.
- **dbt joins.** Joins are inferred from column names only with `--infer-fks`.

**Outcome:**
- **Setup:** `claude mcp add qdbd -- qdbd mcp`, or zero config in VS Code with the QuickDBD extension.
- **Tools:** the agent gets 9 read-only tools.
- **Fixes along the way:** `qdbd path`, selectors and the viewer get correctness fixes for joins and globs.

**Protocol facts this rests on** (checked against the spec, Oct 2026):
- **2026-07-28 ("modern") is stateless:**
  - every request carries `_meta["io.modelcontextprotocol/protocolVersion"]` and `clientCapabilities`;
  - `server/discover` is mandatory;
  - results carry `resultType`;
  - `ttlMs` and `cacheScope` are required on discover and list results;
  - `ping` and `logging/setLevel` are removed;
  - `subscriptions/listen` is a mandatory pattern.
- **Legacy (2025-11-25 and earlier) uses `initialize`.** 2025-03-26 must accept batches.
- **A dual-era server serves both.**
- **The official SDK, `mcp` 2.3.0,** has about 15 dependencies. It's a **dev dependency only** (`mcp>=2.3,<3`), used to prove compatibility.

## Command

`qdbd mcp [PATH ...] [--root DIR] [--infer-fks]`

- **No PATH:** serve every schema project found under the root.
- **PATH...:** serve exactly one project.
  - A `*.json` file is a dbt manifest.
  - A folder holding `manifest.json` and no `.txt`/`.dbml` is a dbt `target/`.
  - Anything else is schema files, as in `build`.
  - Mixing kinds, or a missing path, exits 2 with a message on stderr. Both are checked before stdout is redirected.
- **The root** is `--root DIR` if given, else `$CLAUDE_PROJECT_DIR`, else the cwd. The server `chdir`s there after resolving PATHs, so every output path is relative to the root.
- **Refusal:** with no PATH, it won't scan a filesystem root, the home folder or `%SystemRoot%`. Tools then say "start with `--root DIR` or a schema path".
- **`--infer-fks`:** dbt projects also link `<entity>_id` columns, as `qdbd import dbt --infer-fks` does. These joins are labelled "inferred from column names" in `describe_tables` and `join_path`.
- **Lifetime:** it runs until stdin closes and logs only to stderr.

## Projects: `src/quickdbd_cli/targets.py` (new; Python port of `vscode/src/target.ts` + `schema.ts`)

- **Ported rules:**
  - `has_table` and `looks_like_quickdbd` read the first 5000 lines, and `schema_language` uses `parser.syntax_of` for DBML.
  - `find_target(file, stop_at)` applies the 4 rules of `findTarget` in order: own sidecar, nearest `qdbd.layout.json`, an all-schema folder, the single file.
  - `allSchemas` fails on a dot-folder, `node_modules`, any `*.layout.json` below, or more than 500 files (`MAX_SCAN`).
  - `hasSidecar` looks in the same folder only.
  - Symlinks are not followed.
- **`find_targets(root) -> list[Target]`:**
  - it skips dot-folders and the sidebar `SKIP` list;
  - it stops after 5000 candidate files (`MAX_FILES`) and skips files over 2 MB;
  - its walk budget is about 20k folders or 2 s, and an early stop is reported in `list_projects`;
  - symlinks resolving outside the root are skipped.
- **Shared test cases.** `tests/fixtures/targets/cases.json` holds the cases, and both `tests/test_targets.py` and `vscode/test/target.test.ts` run them, so the two ports can't drift.
- **dbt:** each `dbt_project.yml` with `target/manifest.json` beside it becomes a `kind="dbt"` project.
  - It is compiled in memory: `dbt.import_dbt(..., split=True, infer_fks=flag)` → `compile_sources`, with the import defaults otherwise (root package, sources). Paths are labelled `<dbt:NAME>/staging.txt`, and nothing is written.
  - If generated `erd/` files exist too (first line is `dbt.HEADER`), **both** projects are listed and labelled:
    - "dbt manifest (live)";
    - "generated by `qdbd import dbt`: edit the dbt YAML and re-run the import, don't hand-edit".
- **Naming:** a `Target` is `name` (the file stem or folder name, falling back to the relative path on a collision), `kind`, `root` and `paths`.
- **Freshness:** `find_targets` is cached. It refreshes on `list_projects`, on an unknown project name, and otherwise at most every 5 s.

## Protocol: `src/quickdbd_cli/mcp.py` (new, stdlib only)

- **`Server.handle(msg) -> response | None`** is pure, so tests drive it in-process. `serve()` is a sequential stdio loop; jsrt and ELK aren't thread-safe.
- **Isolation is the first thing `cmd_mcp` does,** before `jsrt.runtime()`:
  1. Duplicate fds 1 and 0 to private fds ≥3 (POSIX `F_DUPFD_CLOEXEC`; Windows `os.dup` then `set_inheritable(False)`).
  2. `dup2` stderr onto fd 1 (devnull if fd 2 is closed) and devnull onto fd 0. On Windows, `SetStdHandle` both.
  3. `sys.stdout = sys.stderr`. Stray prints, C-level writes and child processes then never reach the wire.
- **Framing:**
  - Output is `json.dumps(msg, ensure_ascii=True, separators=(",", ":")) + b"\n"`, flushed after each message.
  - Input is read in binary, decoded as UTF-8 per line, and blank lines are skipped.
  - EOF or a broken pipe exits 0.
- **stderr stays small:**
  - a banner line;
  - one line per failed call;
  - a full traceback only for the first exception of each type, or always with `QDBD_MCP_DEBUG=1`.
- **Classifying a request:** it is *modern* iff `params._meta` has `io.modelcontextprotocol/protocolVersion`. Messages without `method` are ignored.
- **Modern requests** are served the same way whatever the legacy state:
  - **Errors:** missing `clientCapabilities` gives `-32602`; any version other than `2026-07-28` gives `-32022` with `data {supported: SUPPORTED, requested}`, where `SUPPORTED = ["2026-07-28", "2025-11-25", "2025-06-18", "2025-03-26", "2024-11-05"]`.
  - **`server/discover`** returns `supportedVersions: ["2026-07-28"]`, `capabilities {tools: {}}`, `instructions`, `ttlMs: 3600000` and `cacheScope: "public"`. The tool list and instructions hold no user data.
  - **Every result** carries `resultType: "complete"` and `_meta["io.modelcontextprotocol/serverInfo"]`. List results also carry `ttlMs` and `cacheScope`.
  - **`subscriptions/listen`** answers with `notifications/subscriptions/acknowledged` (an empty filter, the request id as `subscriptionId`), then completes.
  - **`ping`** gives `-32601`.
- **Legacy requests:**
  - **`initialize`** echoes a supported legacy version, otherwise answers `2025-11-25`. It returns `capabilities {tools: {listChanged: false}}`, `serverInfo {name: "qdbd", version: __version__}` and `instructions`.
  - **Fields by version:** tool `annotations` from 2025-03-26, `title` from 2025-06-18. Modern-only fields are never sent.
  - **`ping`** returns exactly `{}` in any state.
  - **Batches:** when 2025-03-26 was negotiated, an array is a batch, answered as one array line (nothing if the batch held only notifications); `[]` gives `-32600`.
  - **Before `initialize`,** any other request gives `-32602` with a hint.
- **Both eras:**
  - `tools/list` is in a fixed order;
  - the empty `resources/list`, `resources/templates/list` and `prompts/list` are answered;
  - an unknown method gives `-32601`, and an unknown tool gives `-32602`;
  - bad JSON gives `-32700`, and an array outside the batch case gives `-32600`;
  - notifications get no reply.
- **Tools:**
  - **annotations:** `readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint: false`;
  - **failures** (bad selector, unknown table, git error, JS timeout, unexpected exception) become `isError: true` results with a message the agent can act on;
  - **argument limits:** `select`, `query` and names at most 500 characters, refs at most 200.
- **`instructions`:** about 12 lines on which tool to use when, the selector cheat sheet, and that names in messages may be char-code encoded (`dbo46Order32Line` = `dbo.Order Line`).

## Tools: `src/quickdbd_cli/agent.py` (new)

- **The `project` argument** picks one of `list_projects` (it's named so it isn't confused with database schemas such as `sales.orders`). It's optional when there's one project; otherwise the error lists the names.
- **Cache:** each call re-runs `discover()` on the project's inputs (catching added and removed files). It keys the cached `(Schema, FileParses, model_json)` on the sorted `(path, mtime_ns, size)`; dbt projects key on `manifest.json` + `catalog.json`. A rebuild costs about 35 ms for 200 tables.
- **Names:**
  - normalised: quotes, backticks and `[]` stripped, an optional `public.` prefix, case-insensitive, aliases accepted;
  - unknown names get the 3 closest suggestions;
  - a `select` that is exactly one table's name is treated as that table.

| Tool | Args | Returns |
|---|---|---|
| `list_projects` | – | each project: name, kind, its files (syntax, tables, generated flag), table, relationship and error counts; dbt hints (no relationships → add `relationships` tests or use `--infer-fks`; missing types → `dbt docs generate`) |
| `list_tables` | `select?`, `project?` | one line per table (name, aliases, column count, first doc line), grouped by group; more than 300 tables without `select` gives a per-group summary (count and sample names) |
| `describe_tables` | `tables[]` or `select`, `project?` | per table: file:line, group, tags, doc, generated flag; columns (line, type, PK, FK→target, unique, null, default, doc, DBML enum values); references and referenced-by with cardinality and file:line. At most 25 tables and 60 columns each; unknown names are listed while the rest still return |
| `search_schema` | `query`, `project?` | case-insensitive matches in table names and aliases, column names, table and column docs, grouped; at most 100 |
| `join_path` | `from`, `to`, `project?` | steps with every column pair and cardinality, plus hints ("nullable FK / 0.. end: LEFT JOIN keeps unmatched rows", "1:N: rows multiply", "N:N", "table-level: join columns unknown"); the SQL; "also joinable via …" (true alternatives only, inferred ones labelled); a warning if the project has errors; for dbt, a note to use `{{ ref() }}` / `{{ source() }}` |
| `check_schema` | `strict?`, `file?` + `content?`, `project?` | `OK: N files, N tables`, or `path:line: severity: message` lines (at most 200) plus counts, as a normal result. With `content`, the text for `file` is checked in memory and nothing is written; `file` must be one of the project's files or a new `.txt`/`.dbml` path inside its folder |
| `diff_schema` | `base` (`HEAD`), `merge_base?` (default true unless `base` is `HEAD`), `format?` (`text`/`markdown`), `file?` + `content?`, `project?` | changes since the base, labelled "since main (merge-base abc1234)"; refuses dbt projects |
| `render_diagram` | `select?`, `focus?`, `depth?` (1), `mode?`, `project?` | a PNG (long side up to 1568 px, scale at least 0.6) plus a caption. About 30 tables in `full`, more by switching to `keys`, then `header` (which the caption says); beyond that, "narrow with select/focus" |
| `syntax_reference` | `syntax?` (`quickdbd`/`dbml`) | the condensed guide in new asset `assets/syntax-reference.md` (from `docs/syntax.md`, `docs/dbml.md`, `docs/tags.md`), including that renaming a table loses its saved position |

- **Output rules:**
  - plain, compact, deterministic text written for LLMs, not JSON;
  - one 40,000-character budget per result (Claude Code moves results over 50k to a file), with explicit lines such as "…and 140 more; narrow with `select`";
  - POSIX paths relative to the root, also on Windows.
- **`render_diagram` never calls `project.build`.** It runs `model_json` → `select_model` → `focus_ids`, counts and caps, and only then runs a fresh ELK layout of the subset. The SVG is rendered with `embed_font=False`, then `svg_to_png`.

## Engine fixes (`render.js`, so `qdbd path`, the viewer and MCP all get them)

1. **Composite foreign keys.** `measure.model_json` gives one shared `"k"` to the rels of a composite key. A group is either:
   - one multi-column DBML ref (same path, line and tables);
   - FK rels from one child table to one parent table that point at *different* parent columns which together are exactly the parent's PK (2 or more). This is the QuickDBD style, for example AdventureWorks `SalesOrderDetail → SpecialOfferProduct`.

   Then:
   - `findPath` steps gain `pairs`, and `pathSql` ANDs them;
   - `cli.cmd_path` and the viewer's path list (`viewer.js` pathHtml) show every pair.
2. **Prefer column-level relationships.** Among parallel relationships between two tables, `findPath` prefers column-level ones over table-level ones. Today `OrderLine → Product` in the sample gives `ON ...`.
3. **Schema-qualified names.** `sqlIdent` quotes each dotted part (`"raw.users"` → `raw.users`).
4. **`+x+` in cycles.** The up and down walks get separate visited sets.
5. **Fast globs.** `globRe` collapses runs of `*` and escapes `+`. Today `name:**********Z` takes about 0.5 s on one table, tripling per extra `*`.

## Hardening (existing modules)

- **`jsrt.py`:** `call`/`call_async` take an optional `timeout_sec` (mini-racer supports it). MCP uses 10 s for select, path and neighbourhood, and 60 s for ELK.
- **`diff.py`:**
  - `schema_at_ref` rejects refs that start with `-` or contain NUL, CR or LF (`HEAD@{1 day ago}` stays valid);
  - `_git` gets `stdin=DEVNULL`;
  - a new `merge_base(ref, inputs)` helper.
- **`project.display_path`:** absolute when the cwd is a filesystem root.

## VS Code auto-setup (extension 0.5.0)

- **`vscode/src/mcp.ts`** feature-detects `vscode.lm.registerMcpServerDefinitionProvider` and `vscode.McpStdioServerDefinition`. `engines` stays `^1.85.0`, with local types, so the install floor doesn't rise for Cursor, Windsurf or VSCodium.
  - **`provideMcpServerDefinitions` is silent and cheap.** VS Code calls it eagerly, even in unrelated workspaces. A folder counts when `findFiles` with the sidebar `EXCLUDE` plus `isSchemaFile` finds a schema, or it has a `dbt_project.yml` with `target/manifest.json`. Each such folder gets one definition: command `qdbd`, args `["mcp", "--root", folder]`, `cwd` the folder. There's no qdbd lookup and no prompt.
  - **`resolveMcpServerDefinition`** finds the real executable through `qdbd.found()` (prompts are allowed here). It requires `MCP_MIN_VERSION = [0, 3, 0]`; otherwise it returns `undefined` and gives a one-time "update qdbd" hint.
  - **Refresh:** a change event fires when the set of schema folders changes, or when qdbd resolves or installs.
- **`vscode/src/mcpdef.ts`** (no `vscode` import): pure builders plus the version gate, tested by `vscode/test/mcpdef.test.ts`.
- **`MIN_VERSION` stays `[0, 2, 0]`,** so users with an older qdbd pinned keep every other feature.
- **Cursor auto-setup is left out:** no Cursor build can be tested, and both APIs at once could register duplicate servers. The docs give `.cursor/mcp.json` with `["mcp", "--root", "${workspaceFolder}"]`.
- **`package.json`:** `contributes.mcpServerDefinitionProviders: [{id: "quickdbd", label: "QuickDBD schemas"}]`, `mcp`/`ai` keywords, version `0.5.0`.
- **Tests:**
  - the test API gains `mcpServers()`;
